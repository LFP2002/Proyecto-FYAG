# SPEC-027 — Bloqueos productivos

`FYAG_BLOQUEOS_PERFIL=deshabilitado` es el valor por defecto. `qa_c2` requiere todas las guardas históricas de `FYAG_BLOQUEOS_C2=QA_AISLADO_C2`; ese selector histórico sigue funcionando sin variables nuevas. `produccion` es incompatible con QA y no toma sus IDs ni protege a la última TI. No exige verificar el correo de cuentas históricas para iniciar sesión.

## Puerta operativa

1. En un entorno aislado, ensayar migraciones, las tres recuperaciones y restauración. En producción, aprobar el cambio fuera de banda y registrar una referencia en `FYAG_BLOQUEOS_AUTORIZACION`. Reservar terminal de infraestructura sin grabación para recuperar una TI si el arranque no es posible.
2. Verificar manualmente la entrega real (no solo la aceptación SMTP) a la **misma TI** indicada en `FYAG_BLOQUEOS_CORREO_TI`. Registrar en `FYAG_BLOQUEOS_ENTREGA_SMTP` una referencia verificable de la prueba para el buzón, remitente y transporte configurados. Estas referencias son constancias humanas, no credenciales ni una integración con el sistema de tickets. Repetir la comprobación si cambia la configuración. Usar `FYAG_BLOQUEOS_DOMINIO` para el dominio institucional del remitente y la TI de referencia.
3. Con `DEBUG` desactivado, URL pública HTTPS, cookies seguras, PostgreSQL migrado, SMTP autenticado con TLS/SSL y Redis dedicado autenticado `rediss://` (certificado y nombre verificados), ejecutar `python manage.py validar_bloqueos_productivos` con el perfil productivo en un proceso aislado. Si hay proxy TLS, usar `FYAG_PROXY_TLS_CONFIABLE=CONFIRMADO` únicamente si la aplicación no es accesible sin el proxy y este elimina y reemplaza la cabecera indicada. Revisar `REMOTE_ADDR` efectivo: los límites no confían en `X-Forwarded-For` del cliente.
4. El preflight comprueba migraciones, una TI activa y sin bloqueo con correo verificado, la operación atómica de Redis y el establecimiento de la conexión SMTP. ASGI/WSGI repiten el preflight antes de aceptar tráfico. No se envía correo desde el preflight. Si la TI de referencia queda bloqueada y es necesario reiniciar, usar el procedimiento excepcional desde infraestructura: el comando no necesita Redis ni SMTP. El preflight admite para esa TI una temporal de recuperación vigente con evidencia de contraseña personal previa, para que pueda terminar el cambio obligatorio tras arrancar. No desactivar el perfil para sortear un bloqueo; retirar tráfico antes de un rollback operativo.

El `compose.yaml` de desarrollo fija un Redis sin TLS: no sirve para activar este perfil. Una instalación autorizada debe proporcionar `FYAG_SECURITY_REDIS_URL` con TLS tanto al backend como a los procesos de correo que usan Redis; en Compose se debe sustituir el valor de `environment`, no solo editar `.env`. La separación física y operativa de Redis se verifica en la revisión de infraestructura, además de la comprobación de endpoint que hace el preflight.

## Política y auditoría

Cinco fallos dentro de 15 minutos; bloqueos 15/60/240 minutos y cuarto ciclo dentro de 24 h hasta recuperar. Durante un bloqueo no se amplía el plazo. Login conserva el 401 genérico. 429/503 no cuentan; refresh y primer cambio comparten el límite vigente de 30/min por IP, ahora atómico entre procesos en Redis. La recuperación por correo conserva su vigencia configurada y no requiere una sesión. Los resets TI e infraestructura generan credencial temporal y primer cambio obligatorio.

Solo TI consulta `EVENTO_ACCESO` (`BLOQUEO_TEMPORAL`, `BLOQUEO_TI`, `EXPIRACION`) con autoridad `SISTEMA`, actor nulo y estado anterior/nuevo. El desbloqueo administrativo se proyecta sobre el evento de reemisión existente; correo e infraestructura reutilizan sus registros. El vencimiento se registra al evaluar una contraseña después del plazo; no se crea un evento por cada fallo. No se duplican registros ni se proyectan secretos. Buscar por usuario objetivo, no por actor. Si un cursor anterior deja de ser válido, iniciar una nueva consulta.
