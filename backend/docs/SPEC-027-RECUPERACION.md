# SPEC-027 — Recuperación por correo verificado

Aplicar `usuarios.0016_recuperacion_correo` antes de iniciar backend y consumidor. En Compose se reutiliza `verificacion_correo`, con perfil `smtp` o el override `mailpit` para QA. SMTP admite cualquier proveedor configurado de acuerdo con la [guía de correo](SPEC-027-VERIFICACION.md). La UI comienza en **¿Olvidaste tu contraseña?**. El token va en un fragmento, se borra del historial y se presenta solo en el JSON del POST. No registrar cuerpos HTTP ni datos SMTP en trazas.

- Las cuentas activas de los seis roles pueden recuperar acceso si su correo vigente está verificado y su credencial es `PERSONAL`, o está en `RECUPERACION` con evidencia de una contraseña personal previa. `INICIAL` y las reemisiones históricas sin evidencia conservan el primer cambio obligatorio; no se acusa recibo de forma distinta. La migración reconoce los eventos históricos de primer cambio sin modificarlos.
- La solicitud 202 no confirma una cuenta ni promete entrega. El consumidor consulta elegibilidad; las colas privadas de verificación y recuperación están separadas y acotadas. Recuperación solo guarda en Redis dirección y tiempo de solicitud, nunca el token. El enlace de 256 bits caduca en 15 minutos por defecto. `FYAG_RECUPERACION_MINUTOS` acepta enteros de 5 a 30 inclusive; valores inválidos impiden el arranque. El cambio se aplica a nuevas emisiones y las dos plantillas informan la vigencia usada. Las solicitudes repetidas no reemplazan ni extienden el enlace. Si SMTP falla o la entrega es incierta, esperar a que expire antes de volver a solicitarlo. No hay reintento SMTP automático. Si Redis no está disponible, la API devuelve 503.
- Confirmar no cambia correo, rol o actividad. Se elige una contraseña personal, se revocan JWT, refresh, sesión Django y tickets de chat por cambio de versión; las conexiones abiertas se cierran en la siguiente revalidación o latido. No se inicia sesión automáticamente. La notificación SMTP posterior no revierte el cambio si falla. La auditoría `RecuperacionCorreoEvento` representa titularidad del buzón, sin emitir eventos de reemisión TI.
- En QA C2 y con el [perfil productivo opt-in](SPEC-027-BLOQUEOS.md), una recuperación confirmada limpia el bloqueo; un estado de acceso incoherente se rechaza. La [recuperación excepcional por infraestructura](SPEC-027-RECUPERACION-TI.md) es un procedimiento separado y exclusivo para TI.

Solo `ADMINISTRADOR_TI` ve estos eventos en Auditoría (fuente `RECUPERACION_CORREO_EVENTO`) y en el historial de Usuarios y roles. Ambas vistas leen el mismo registro, sin copiarlo ni atribuirlo a una cuenta autenticada: la autoridad es **Titularidad del correo**. Buscar por cuenta objetivo (`recurso_tipo=USUARIO`, `recurso_id`), no por actor. El estado de acceso anterior se muestra cuando consta.

**QA:** usar únicamente usuarios sintéticos `.test` y Mailpit privado. En el laboratorio C2, con `POSTGRES_DB=fyag_spec018c_c2_qa`, Redis de seguridad y Mailpit configurados, ejecutar `FYAG_QA_RECUPERACION_MAILPIT=1 python manage.py test apps.usuarios.tests.test_recuperacion_correo_027`. Para [Postman](postman/SPEC-027-recuperacion.postman_collection.json), conservar el cookie jar; ejecutar 01–02, leer el fragmento de Mailpit y configurar `token_qa` y `clave_qa` solo en variables locales privadas. Ejecutar 03–04; limpiar variables y no exportarlas. El [contrato OpenAPI](openapi/SPEC-027-recuperacion-v1.yaml) documenta CSRF, límites y respuestas.
