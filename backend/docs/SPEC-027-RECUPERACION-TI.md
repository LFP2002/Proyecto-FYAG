# SPEC-027 — Recuperación excepcional de Administrador TI

Usar únicamente si no se dispone de un camino ordinario de recuperación apropiado. El comando no concede acceso al servidor: el control de acceso del sistema operativo y el procedimiento humano son condiciones de uso. No existe endpoint HTTP ni automatización para este mecanismo.

1. Dos personas identificadas y autorizadas validan fuera de banda el incidente, la identidad institucional del titular y el ID exacto de su cuenta TI existente y activa. Registrar su aprobación en el sistema institucional y conservar una referencia trazable. Usar una cuenta nominativa de infraestructura autorizada; el identificador escrito en el comando debe corresponder al operador de la sesión. El comando no verifica un ticket externo ni sustituye ese control humano.
2. Abrir una terminal controladora POSIX privada, en primer plano, sin grabación, eco de entrada, redirecciones, pantallas compartidas ni transcripción de E/S. Desactivar `DEBUG` y comprobar que ni servidor SQL ni intermediarios registran valores de consultas. Desde `backend/` ejecutar `python manage.py recuperar_acceso_ti`, **sin parámetros**. Introducir el ID, operador, referencia y motivo sin secretos. Verificar la cuenta presentada y escribir `RECUPERAR <ID>` para confirmar; cualquier otra respuesta cancela.
3. La credencial se muestra una sola vez y solo después del commit. Entregarla al titular verificado por un canal confidencial aprobado, de un solo uso o presencial. No enviarla por SMTP, chat, tickets ni capturas. El titular ingresa por el flujo normal antes de la caducidad de credenciales temporales y cambia la contraseña; después inicia sesión manualmente. Si la terminal se pierde después del commit, la credencial no se puede consultar: verificar el evento y obtener autorización para una nueva emisión.

La transacción adquiere mutex administrativo, usuario, credencial y, si el perfil de bloqueos está activo, estado de acceso; después invalida los desafíos de primer cambio, cambio de correo y recuperación por correo. La versión de sesión invalida JWT, refresh y el acceso WebSocket mediante las comprobaciones existentes. El correo vigente o pendiente no se modifica; la verificación de titularidad del correo vigente es independiente de la sesión y se conserva. No se crea ninguna sesión, usuario ni rol. Si el estado requerido falta o es incoherente, se aborta sin repararlo. SMTP y Redis no intervienen en el comando. La guarda de recuperadoras se mantiene exclusivamente en QA C2; ver el [procedimiento productivo opt-in](SPEC-027-BLOQUEOS.md).

La migración `0017_recuperacion_ti_infraestructura` crea el registro protegido contra modificación y borrado de filas. Auditoría (`RECUPERACION_TI_EVENTO`) y el historial de Usuarios y roles lo leen sin duplicarlo, solo para `ADMINISTRADOR_TI`: cuenta, fecha, autoridad `INFRAESTRUCTURA`, operador, referencia, motivo y estado anterior cuando consta. No contiene credenciales, hashes ni tokens. El filtro por actor autenticado lo excluye; buscar por `recurso_tipo=USUARIO` y `recurso_id`. Si un cursor de Auditoría emitido antes del cambio deja de ser válido, iniciar una consulta nueva.

**Solo laboratorio C2:** no se emite una temporal a una recuperadora configurada si con ello no queda otra TI QA con contraseña personal y acceso operativo. Completar el cambio obligatorio y comprobar el nuevo inicio de sesión antes de recuperar a la segunda TI. Esta guarda no se aplica fuera de C2.
